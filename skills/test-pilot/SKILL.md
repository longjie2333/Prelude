# test-pilot

你独自完成一次完整的测试：用户只给了一个目标，最后要拿到一份可信的报告。目标是**更快地发现问题，尤其是测试人员没覆盖、没注意到的地方**。

## 原则

- **只打断一次**：接收阶段把所有缺少的信息一次问完，之后自己判断，把假设写进报告。
- **证据优先**：没有可执行复现脚本的缺陷不算缺陷。宁可少报，不要误报。
- **预期值要有依据**：来自文档、接口契约、规范或不变量（守恒、幂等、单调、往返一致），不能抄实际输出，也不能凭自己猜的业务规则。
- **不越界**：只访问授权范围内的主机；被拒绝的操作不要换个方式重试，记入"没测什么"。不在用户主机上安装被测程序（exe 放 Windows Sandbox 或虚拟机，apk 放模拟器）。
- **先广后深**：先把功能面过一遍，再在风险最高的地方深挖。时间花在最可能出问题的地方。

## 流程

每进入一个阶段，调用 `test_progress`。

### 1. 接收（intake）

1. 判断目标类型：网站、接口、安卓 apk、Windows 程序、CLI、服务等，可以同时属于多类。
2. 读项目的 `.prelude/notes/` 和 `AGENTS.md`，读已有的相关类别经验（如果有）。
3. 能从目标本身拿到的信息先自己拿：接口文档（`/openapi.json`、`/swagger`）、首页、`--help`、README、安装包元数据。
4. 按 [references/intake.md](references/intake.md) 列出仍然缺少的信息，用 `questionnaire` **一次性**问完。信息已经足够时可以不问。没有 UI 时 `questionnaire` 会失败：按保守的默认值继续（只做功能测试、不做破坏性操作），并把假设写进报告。

### 2. 勾勒轮廓（profile）

探索目标，弄清：功能面、接口与参数、角色与权限、数据流与状态、技术栈、外部依赖、如何重置数据。把这些写进 `.prelude/notes/`（每个主题一个文件），下次测试可以直接用。

### 3. 确定方向

用户指定了方向就按用户的。否则按"风险 × 盲区"排出优先级：

- 风险：涉及钱、库存、权限、数据完整性的地方优先；写操作优先于读操作；新功能和复杂逻辑优先。
- 盲区：对照 [references/blind-spots.md](references/blind-spots.md) 至少过一遍，每一项判断是否适用、怎么测。

在心里或 `.prelude/work/plan.md` 里列一份简短的测试清单，按优先级执行。

### 4. 选工具

先用成熟工具和已有工具：知识库里的工具、用户已配置的 MCP（例如浏览器自动化）、Playwright、adb、curl。缺了再在 `.prelude/work/` 里自己写。首次安装依赖需要用户批准，没有批准就用语言自带的能力（Node 内置 `fetch`、Python 标准库）。

### 5. 执行（execute）

对每个怀疑点：

1. 写复现脚本，按 [references/repro.md](references/repro.md) 的约定。
2. 运行它，确认确实复现（退出码非 0），并且问题修好后会以 0 退出。
3. **立刻**调用 `finding_record` 记录：标题、严重程度、类型、描述（发生了什么、预期是什么及依据、步骤）、脚本路径、证据文件。

`finding_record` 会在调用时冻结脚本和证据（按哈希复制），之后再改文件不影响复验。脚本需要修改时，在复验前用 `finding_record` 带 `id` 替换。

体验问题（UI/UX、文案、可用性）记为 `suggestion`，不需要复现脚本，但描述要具体：在哪里、什么问题、为什么影响用户、建议怎么改。

### 6. 复验（verify）

测完后调用一次 `verify_findings`。代码会在干净目录里重跑每个缺陷的脚本 3 次（复现率 ≥ 60% 才算复现），再交给一个看不到测试过程的审查员判断脚本是否真的证明了问题。只有复验结论为 `confirmed` 的才进入报告的"已复验缺陷"或"建议"。

未复现或被拒绝的：看原因。如果是脚本写得不对（依赖残留状态、断言过强、偶发），可以改好后用 `finding_record` 记成新发现再复验；原来那条留在"未复现项"里。

### 7. 报告（report）

按 [references/report.md](references/report.md) 写到 `.prelude/reports/<日期>-<主题>.md`，然后调用 `report_finalize`。它会检查必需小节，以及每个发现 id 是否放在和复验结论一致的小节里；有问题时会列出全部问题，改好再调用。

### 8. 复盘（retro）

- 更新 `.prelude/notes/`：这个系统的新事实、坑、环境差异、怎么重置数据。
- 有知识库工具（`kb_*`）时，按它们的说明写入跨项目通用的经验和工具；经验必须引用本次已复验的发现。没有可沉淀的就明确说明。
