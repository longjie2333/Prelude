# 真实模型运行：canary × DeepSeek-V4.1-Flash，知识库两台"机器"（2026-10-27，M2）

> plan §7 M2 验收。两台"机器"先后测同一个 canary，共享一个本地 bare 远程作为知识库；第二台是另一个项目 id，从第一台留下的经验开始。

| 项 | 值 |

## 分析

- **"第二次命中更快"（plan §0 成功标准 2）没有被证明。** B 比 A 慢（23.8 对 17.7 分钟），并且两次找到的缺陷相同。经验确实改变了 B 的做法：它直接按 `les-85a9` 做了交错探测、按 `les-0108` 把 schema 当断言，但 A 在没有经验时也找到了全部 6 个。canary 太小、缺陷太典型，第一次就能全部找到，经验没有提升的空间。要验证这条标准，需要一个第一次找不全的目标，或者让第二个目标是"同类但不同"的系统（M3-5 的评测）。
- **复盘的成本约 4–5 分钟。** 大部分花在写工具上：A 的 selfcheck 一度因为在同一进程里用 `spawnSync` 起服务而死锁，又遇到 Git Bash 改写 `/orders` 路径的问题（它把这条写进了工具 README 的"已知失败"）。
- **B 的探测阶段比 A 长**（11.7 对 7.2 分钟），调用了 9 次 `finding_record`、最后是 7 条发现（2 次是带 `id` 的替换），说明它在边测边改复现脚本。
- **报告与实际写入不一致过一次。** B 的报告草稿写了一条它并没有做的 `kb_lesson_add`，模型在 `report_finalize` 前自己发现并改正。`report_finalize` 只检查"有没有写入"，不核对复盘一节写的内容和审计是否一致。
