# 环境与操作手册（canary）

## 运行环境

- 被测服务：http://localhost:4100（单进程，内存态，无鉴权）
- 测试端：Windows + Node v22.23.2，脚本只用内置 `fetch`，无 npm 依赖
- 测试结束前已 `POST /reset {}` 恢复种子状态（商品 p1..p7，库存 10/5/100/25/3/12/40；订单为空）

## 数据重置

- `POST /reset {}` → 恢复种子库存、清空订单、订单号重置为 `o1`
- `POST /reset {"stock":{"p5":1}}` → 只覆盖指定商品库存，其余保持种子值
- 未知 id 会被忽略；**负数会被接受**（见 known-issues #4）

## 怎么稳定复现并发问题

- 用 `Promise.all` 同时发 N 个 `fetch`，HTTP/1.1 keep-alive 下 N=2 就足够触发；N=10 几乎 100%
- 每个探测脚本开头必须先 `/reset`，否则前一轮的订单/库存会污染结果
- **不要在同一个服务上并行跑多个探测脚本**：它们都调用 `/reset` 并共享 p5，会互相串扰，产生"偶发 404""订单列表混入别的订单"这类假阳性。本轮因此误判过两次，见 known-issues「探测时踩过的坑」

## 写复现脚本的注意点（本机验证过）

- heredoc 写 `.mjs` 时，`fetch(url,{method:"POST"})` 里的 `method:"POST"` 容易被写成 `method:"POST"}`（丢右括号）—— 本轮出现 5 次语法错误。写完先 `node --check`。
- 断言前打印"预期值 + 依据"，审查员只看输出判断。
- 对照路径（顺序调用应当正确拒绝）要写进脚本，能直接排除"断言过强/误报"。
