## 分析

- **覆盖面更好，成本没降。** 同样一句话，旧实现只测到超卖一类；Prelude 按 Skill 的盲区清单把分页、编码、边界都过了一遍，找到了全部三个预置缺陷。但目标被扩大了：驱动在接收问题"是否顺带覆盖同类问题"上自动选了第一个选项"顺带覆盖"，所以两次运行的范围并不相同，耗时对比偏向旧实现。
- **探索阶段太长。** 从开始到第一次记录发现用了 27 分钟、120 次 bash（主会话共 136 次），违背 Skill 中"发现就立刻记录"。模型同时跑多个探测脚本、彼此 `/reset`，然后花了大量轮次排查自己造成的假象（上面的四个未复现项）。
- **审查偏重。** 6 个审查会话共 63 轮、13.8 分钟。审查员普遍不只重跑一次，而是自己设计对照实验；结论质量高（理由都引用了 openapi 原文），但这是可以收的成本。
- **一次无法诊断的拦截。** 审计按设计只记入参摘要，事后看不出审查员那条命令是什么。如果是 `cp .prelude/evidence/... /tmp` 这类只读 evidence 的命令，属于"提到受保护路径 + 出现 cp"的误报。

## 本次运行发现并已修复的问题

| # | 问题 | 修复 |
|---|---|---|
| 1 | `pi -p "/test …"` 和 RPC 下，`/test` 用 `sendUserMessage` 启动测试后立即返回；print 模式随即销毁会话，测试还没开始就结束 | print/json 模式下 `/test` 等到 `agent_settled` 再返回；e2e 改为只 `await prompt()`，去掉 fix 后 3 个用例失败 |
| 2 | `questionnaire` 只支持 TUI，RPC 客户端（有 select/input 对话框）下直接失败 | RPC 下逐题用 `select`/`input` 询问 |
| 3 | 审查子会话的 token 用量没有任何记录（无会话文件） | 写入审计 `verification` 事件的 `detail.reviewUsage` |

## 仍未解决（交给下一步）

- 成功标准 §0-1（更快、更省）未达到。可能的方向：Skill 要求探测脚本串行、不互相重置状态，并在 profile 阶段设时间上限；审查提示限制"最多重跑一次、不自行扩展实验"。改动后需要再跑一次对比，并保持接收问题的回答与目标范围一致。
- 第 4 条验收中的三种越界情形缺少真实运行证据。
- 审计只记摘要导致拦截无法诊断：是否记录被拦截命令的截断文本，需要用户决定（涉及"入参只记摘要"的约定）。
- `skills/test-pilot/` 在本次运行中被完整遵循（阶段、questionnaire、复验、报告小节都对），但上面两条行为问题说明它还需要改。
