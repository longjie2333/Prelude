## Conclusion

会超领。http://localhost:4100 的 POST /coupons/SAVE10/claim 在并发下确实超领，是已确认（独立验证器确认）的缺陷，根因与下单接口同源：remaining 的扣减是读-改-写（lost update）竞态，无原子性/锁保护。

关键证据（SAVE10 经 POST /reset 置为 quota=5 / remaining=5）：
- 每轮 36 个请求，并发度 2/4/8/12 分别接受 9/17/35/36 个 201，均 > 5；结束后 remaining 为 0~1，不等于「起始 remaining − 成功数」（例如 36 次成功、期望 −31），违反规格「remaining 永不低于 0」。5/5 次相同参数复现全部失败。
- lost-update 签名直接可见于响应体：单波并发中多个成功请求返回相同 remaining（K=12 时 12 个请求全部返回 remaining=4；K=8 时 remaining=4 出现 8 次），而串行对照中每个值恰好出现一次。
- 串行对照（并发度 1、20 次请求）完全合规：恰好 5×201 + 15×409，remaining 严格递减 4,3,2,1,0，最终 0 → 超领是并发特有，不是计数器整体损坏。
- 无 5xx、无传输错误，且从未观察到 remaining 高于起始值 → 测量未被外部重置污染，失败不是压测假象。
- oracle 自检：同一 oracle 对进程内注入的竞态参考实现报违规（R1/R2/R3，36>5），对互斥锁串行化实现报 0 违规 → 既会 fail 也会 pass。

说明与建议：本次为独立复现，与前一次对 /orders 库存超卖、coupon 超领的结论一致，同一竞态类影响库存与优惠券两种共享配额资源（严重度高，属一致性问题）。修复方向：对 remaining 使用原子条件更新（如 WHERE remaining >= 1 的数据库条件写）、行锁或串行化临界区，并把「校验 + 扣减」放入同一原子操作；不要依赖响应头 x-consistency: sync 作为并发安全依据。
