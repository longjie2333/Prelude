# Test report — i-20261026-8dad24

> 测一下 canary（http://localhost:4100，接口文档在 /openapi.json）的下单接口在并发下会不会超卖

## Conclusion

会超卖，而且是确定性、严重的超卖。canary 的 POST /orders 在并发下存在 check-then-decrement 竞态（丢失更新）：

确认的结论（均经独立验证器确认）：
1. 超卖成立：p2 库存设为 5，20 个并发 qty=1 下单，全部返回 201（0 个 409），即 5 件库存卖出了 20 件；5/5 次全新 reset 均复现。
2. 最极端场景同样成立：库存=1 时，20 个并发 qty=1 下单仍全部 201（p2、p5 各 3/3 次复现），1 件库存卖出 20 件。
3. 独立实现交叉验证：不依赖被测框架，用 Python 原始 socket 与 curl --parallel 两套独立负载生成器，6/6 次均得到 20×201、最终库存 4，排除了单一 harness 的假阳性。
4. 按“数量”而非“笔数”超卖：p6 库存 12，24 个并发请求 qty 循环 1~3（共 48 件），全部 201，接受 48 件；3/3 次复现。qty=2 场景下 p6 库存 12 接受 60 件（4/4 次）。
5. 根因证据：库存并非按订单逐笔扣减（丢失更新）。接受 20 笔订单后存储库存只减少了 1（5→4），与规格隐含的 -15 不符；N=2/5/10/20 共 16/16 次试验均如此，说明并发请求读到同一份旧库存并各自“扣减 1”后互相覆盖。
6. 缺陷是并发特有的：同一批 25 个请求串行执行得到恰好 5×201 + 20×409、最终库存 0，符合文档语义，说明规格本身可满足，问题在并发控制。

未发现的其他问题：POST /reset 的库存覆盖稳定生效（6/6）；取消路径在并发下正确——同一订单 id 的 10 个并发取消只产生 1×200 + 9×409，库存未重复返还（3/3）。缺陷范围局限于下单接口的检查-扣减临界区。

最小复现：POST /reset {"stock":{"p2":5}} → 同时发出 20 个 POST /orders {"productId":"p2","qty":1}（需保持长连接/预开 socket，使请求在同一瞬间到达）→ 观察 20×201、GET /products/p2 库存为 4 而非 0。

## Notes

证据要点与限制：
- 缺陷是时序敏感的：用 N 个独立 curl 进程（各自 TCP 握手造成错峰）时未能复现（1×201 + 9×409）。必须用 keep-alive 连接/预开 socket 同时发出，这一点应在回归用例中固化。
- 侦察阶段另发现两个规格偏差（非本次目标、仅观察）：GET /products 分页不一致——total=7/pages=3 但只返回 p1..p6，p7 只能通过 GET /products/p7 访问；page=0/size=0 被静默改为默认值而非报 400。另外所有响应带未文档化的 x-consistency: sync 头。这些未经独立验证器确认，属未确认观察。
- 隔离级别与环境污染：执行者自述有一次「库存虚增」现象实为两个并行实验同时调用 POST /reset（该接口重置全部商品）造成的自身干扰；报告中已排除，非 SUT 缺陷。
- 能力缺口：cap:http-client 与 cap:concurrency 两个模板能力在环境中不可用，执行者自行实现，故超卖结论的可信度主要依赖两套独立负载生成器的交叉验证与原子 mock 的 oracle 自检（对原子 mock PASS、对超卖 mock FAIL）。
