## 本次运行暴露并已修复的问题

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | pi 的 bash 工具没有默认超时。模型直接运行 Chromium 的 `chrome.exe` 查版本，Windows 上它启动了浏览器进程而不退出，这次调用 13 分钟没有返回（最后由我结束该进程树） | 轮廓阶段多出 13 分钟 | 测试模式下，没有设超时的 bash / powershell 调用默认 600 秒（D-25）；模型自己设的超时不变 |
| 2 | `finding_record` 的 `id` 只用于替换已有发现，模型却用它给新发现编号（第二条传 `f-002`），25 次调用中 11 次报"no finding f-002"失败、重试 | 浪费轮次 | `id` 等于下一个编号时按新增处理；其他不存在的 id 报错时列出已有 id 并说明"新增不要传 id"；参数说明同步修改 |
| 3 | 命令分析把 `npm install playwright 2>&1` 里的 `2>` 当成第二个包名，审批被拦，模型两次安装被拒 | 安装 Playwright 多绕了几轮 | 包名解析遇到重定向即停止；补了回归测试 |
| 4 | 驱动只支持 canary | — | `RUN_TARGET` / `RUN_ALLOWED` / `RUN_ALLOW_INSTALL` |

修复 1、2、3 都晚于这次运行，这次运行用的是修复前的代码。

## 分析

- **超时的主因是执行阶段没有收口。** 去掉卡住的 13 分钟，轮廓阶段仍有约 6 分钟，接近限时；但执行阶段 53 分钟里模型一直在补探测（第 5 个 UI 脚本、搜索、状态推进按钮），到被中止时还没有调用 `verify_findings`。Skill 写了"清单和盲区过完就进入复验"，但没有针对整次测试的时间预算，模型也不知道外部有 75 分钟的上限。
- **发现的质量看起来高**：每条都有具体接口、参数和观测值，f-004 还给出了源码依据；但没有经过代码重跑和独立审查，不能计入已复验缺陷。
- **数据约束被遵守**：写操作只用自建、随后删除的 `prelude-test` 数据或不存在的 id。
- **token 很高**（1130 万 processed），主要是 186 轮对一个不断变长的上下文的重复发送。
