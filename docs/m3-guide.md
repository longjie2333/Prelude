# M3 真实运行指南（测试人员执行）

> plan §8 M3 的真实运行由测试人员在自己的环境里执行。本文写每一项怎么跑、怎么把结果交回。

## 通用步骤

1. **准备一个干净的项目目录**（不要用本仓库）：`mkdir ~/prelude-runs/<名称> && cd ~/prelude-runs/<名称>`。
2. **写授权范围** `.prelude/scope.json`（格式见 [README](../README.md#授权范围-preludescopejson)）。只写你授权的目标和测试类型。
3. **启动 pi 并加载 Prelude**：`pi -e <本仓库路径>`。用你平时的模型；要和已有记录对比时用 `magpie/trae-cn/deepseek-v4.1-flash`。
4. **开始**：`/test <一句话目标>`。目标里写清：
   - 地址和环境（测试 / 预发 / 生产）；
   - 不允许做的事（例如"不删除已有数据，新建数据名称带 prelude-test"）；
   - 账号（只写测试账号）；
   - **时间预算**，例如"60 分钟内完成，留出复验和报告的时间"。上一次网站运行就是因为没有预算，到 75 分钟还在探索、没有出报告。
5. **回答一次接收问题**，之后尽量不干预。如果它明显卡住或偏离目标，用 `Enter` 发一句引导，并记下来（这本身就是结果）。
6. **等它说"测试完成"并登记报告**（`report_finalize` 成功）。超过预算还没收尾，就发："停止探索，现在调用 verify_findings，写报告并调用 report_finalize。"
7. **收集结果**（见下文"交回结果"）。

## 各项要点

### M3-1 网站 / UI

- 需要：网站地址、测试账号。本机若没有 Playwright，模型会请求安装 `playwright`，批准即可（会装在项目目录）。
- 看：是否用浏览器测了界面（截图在 `.prelude/work/` 下）、体验问题是否记为"建议"、复现脚本是否能在复验时重跑。
- 可以直接重测上次的团购网站（`8.155.17.234:50080`，仅 functional），和 [上次运行](runs/2026-10-27-web-groupbuy/README.md) 对比。

### M3-2 安全

- 需要：一个**你有权授权**的目标，在 `scope.json` 中写 `"allowed": ["functional", "security-check"]`。没有 `security-check` 时扫描器会被拦截。
- 扫描器（ZAP、nuclei 等）首次安装需要批准；也可以不装，模型会自己写探测脚本。
- 看：扫描器的告警有没有被直接当成缺陷（不应该）；每个安全缺陷是否有一个具体的复现脚本（换 token、换 id 等）。

### M3-3 安卓 apk

- 需要：模拟器或测试机，`adb devices` 能看到它；apk 文件；测试账号；后端环境。
- 目标里写上 apk 路径和设备序列号，例如"用 emulator-5554 测 ./app-debug.apk"。
- 看：是否用 `adb -s <序列号> install` 装在设备上（本机安装会被拦截）；证据是否有截图和 logcat。

### M3-4 Windows 桌面

- 需要：Windows Sandbox 或虚拟机。**在其中**安装 Node、pi 和本仓库，并在 `scope.json` 里加 `"isolated_host": true`（表示这台机器是一次性的，允许安装被测程序）。不要在你的主机上设这个字段。
- 安装包放进隔离环境，目标里写安装包路径。
- 允许只做到"能安装、启动并完成冒烟测试"。
- 看：控件自动化是否可用（pywinauto 类）；用截图得出的结论是否在报告里标明。

### M3-5 评测

需要两组对比，同一个模型、同一句目标、同一个目标系统：

| 组 | 怎么跑 |
|---|---|
| 直接对话 | 在一个空目录启动 `pi`（**不加** `-e`），直接把目标那句话发给它 |
| Prelude | 按通用步骤 `/test <同一句话>` |

- 对 canary：在本仓库执行 `npm run canary` 起服务，两组各跑一次。直接对话组没有闸门，不要对真实系统这样做，除非你接受它没有任何限制。
- "第二次更快"：用同一个 `~/.prelude` 知识库，先测系统 A，再测**同类但不同**的系统 B（例如两个都有库存/订单的服务），看 B 是否读到了 A 的经验、找到问题是否更快。
- 记录：耗时、发现数、你判断的误报数、漏掉的问题。

### M3-6 整理

在任意 pi 会话里运行 `/prelude-kb`，把输出贴回来；有长期未证实或疑似重复的经验时，说明你认为该怎么处理。

## 交回结果

每次运行结束后，在本仓库根目录执行：

```bash
REDACT="密码1,密码2" node scripts/collect-run.mjs <项目目录> <日期>-<名称>
```

例如 `node scripts/collect-run.mjs ~/prelude-runs/web2 2026-10-28-web-groupbuy-2`。它会：

- 把报告、发现、运行状态、系统笔记、复现脚本复制到 `docs/runs/<名称>/`，并把 `REDACT` 中的字符串替换成 `<redacted>`；
- 生成 `summary.json`：阶段耗时、复验结论、token（从 pi 的会话文件读取，需要会话保存是开启的）、知识库写入、拦截、审计链校验；
- 生成 `README.md`：上半部分是自动汇总，下半部分是"测试人员记录"空栏。

然后：

1. 填写 `README.md` 的"测试人员记录"。最有价值的是**发现是否属实**和**漏掉了什么**：只有你知道真实答案。
2. 检查 `docs/runs/<名称>/` 里没有残留的密码或密钥。
3. 告诉我目录名（例如"看一下 docs/runs/2026-10-28-web-groupbuy-2"）。我会读这些文件，对照验收条件，修 Prelude 暴露出的问题，并更新 plan §10。

不需要提交，我来提交。运行过程中出现的异常（卡住、崩溃、报错）也请在"其他观察"里写下当时在做什么。
